# STE Writing (always on)

Apply the `ste-writing` skill's discipline to all prose you write or edit: documentation, READMEs, PR descriptions, comments, error messages, release notes, commit messages. Never to code, identifiers, file paths, or command syntax.

Invoke the `ste-writing` skill for the full rules and the two modes (strict, STE-flavored). Until then, hold every prose draft to this checklist:

- One name for one thing. Never two names for the same item in one piece of text.
- Short common word wins: start (not begin), use (not utilize), help (not facilitate), make sure (not ensure), before (not prior to), after (not subsequent to), get (not obtain), show (not demonstrate).
- No marketing adjectives: seamless, robust, powerful, cutting-edge, effortless, world-class, next-generation, revolutionary.
- Active voice. "The parser reads the file", not "the file is read by the parser".
- Plain verbs. "Analyze the log", not "perform an analysis of the log". No stacked auxiliaries.
- One instruction per sentence. Max 20 words for an instruction, 25 for a descriptive sentence.
- No contractions. Use articles: a, an, the, this, these.
- No semicolons. No em dashes.
- One topic per paragraph, max six sentences. Steps: numbered list, one action per item, imperative form, condition before command.

Before returning prose, self-lint: split over-cap sentences, replace semicolons with periods, expand contractions, make passive voice active, swap nominalizations and phrasal verbs for plain verbs, unify names.

Pairs with the "No AI Slop" output style. The rule guards prose artifacts in every session; the style covers conversational output when selected.
